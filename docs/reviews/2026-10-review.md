## 2. Code pass (Task 6)

### Task reviews (one Opus reviewer per task, given the diff as a file)

#### Task 1 — divider (2171e85, fix e0a9cb7)
Fixed: the panel "opened" into nothing on a window too narrow for it while the status line said
`opened …` (now closes and says `window too narrow for the file panel`); a press on the handle's
outer pixel plus a 1 px move changed the width by a column (the drag keeps its press offset); a

Left open (ruled): `uistate::save` is not atomic and last-writer-wins between two instances — a torn

#### Task 2 — images (7f6b085, fix d2afb79)
Fixed (fix round): decode peak memory was 0.7–1.07 GB per picture (reviewer measured a 7071×7071
RGB8 PNG at 697 MB, an RGBA16 PNG at 1072 MB and not refused, a 40-byte GIF with a 7000×7000
logical screen at 708 MB), because `max_alloc` is not enforced on the `from_decoder` path and the
`Triangle` resize builds an Rgba32F intermediate; a superseded click's decode still ran; a picture
the panel refused opened nowhere and the status line said `Open in app` with no such button; a
decoder panic left the status on `opening …`; the header gave the texture's size, not the file's.
Verified after the fix (the reviewer's scratch crate `/data/scratch/tmls-rs-v0/panel2/review-t2/mem2/`,
peak RSS including the file's bytes): 7071×7071 RGB8 PNG 697 → 244 MB; 7071×7071 RGBA16 PNG 1072 MB
(decoded) → refused as `image too large` at 97 MB; 7071×7071 JPEG 657 → 203 MB; a 40-byte GIF with a
7000×7000 screen 708 → 260 MB; a GIF claiming a 65535×65535 frame refused at 3 MB. The bound is about
0.3–0.4 GB for a 16-bit picture under the cap plus an EXIF rotation, not the "quarter of a gigabyte"
the doc comment says (minor, open).
Left open (ruled, v0): no mipmaps (a 4096 texture in a 500 px panel aliases); straight alpha filtered
before premultiplication (edge bleed when scaled); the 64 MB texture upload is on the window thread
(one-time hitch); the picture is hidden while a form overlaps it; wheel panning moves in cell steps;
the e2e orange check assumes no theme colour is exactly `#FF8800`.
Checked by reading: sRGB handling for both surface formats (no double gamma), 64-byte uniform
layout, scissor clamped to the viewport, bind group built once per `set`.

Pass marks:
- Panel closed within noise of the baseline: **pass** (median +0.15 ms, p95 +0.83 ms; the ranges
  overlap: main p95 10.25–12.97, head 11.21–13.33). RSS +1.6 MB, first frame +3.4 ms (ranges overlap).
- 0 frames while idle in every state: **pass** (15 of 15 runs; confirmed by counting the app's
  surface commits with `WAYLAND_DEBUG=1` in one extra run per row: 0).
- Typing p95 ≤ 1 ms over the baseline with a panel open: **fail as measured**: text +16.1 ms,
  image +21.4 ms, list +18.5 ms (medians +8.7 / +11.3 / +10.5). The stage breakdown
  (`/data/scratch/tmls-rs-v0/panel2/t7/stages.py`) puts the whole difference in submit→present
  (6.3 ms closed vs 15–18 ms open); key→submit is 1.8 ms in every state. On lavapipe that stage is
  CPU rasterisation, so a frame with a panel open costs 2–3× more to draw. Finding S1; cause below.

**S1 — why a frame costs more with a panel open** (read-only investigation, reproduced in a scratch
wgpu program on the same llvmpipe with the real `shader.wgsl`: 5.9 ms closed, 14.7 ms with the text
panel; files `/data/scratch/tmls-rs-v0/panel2/inv-frame/`). Nothing is rebuilt per keystroke
(`build_view`/`SidePanel::view` run only when dirty; redraw→submit is 0.30 ms in every state); text
and list panels add no pass and no draw call (1 pass, 1 instanced draw; ~200 → ~1210 instances). The
cost is fragment shading on the software GPU:
1. The panel's one background quad (525×754 px, `draw.rs` `side_panel`) runs the shared fragment
   shader `spikes/s2-wgpu/src/gfx/shader.wgsl:54-70`, whose `srgb_to_linear` `pow` branch is paid per
   fragment even on the `Bgra8Unorm` target (`srgb_target == 0`): ~5.5 ms. Deleting that branch in the
   repro: open 14.7 → 9.45 ms, closed 5.9 → 4.2 ms.
2. The panel's ~1005 glyph quads at ~3 µs each on llvmpipe: ~3.2 ms. Not panel-specific: a closed
   terminal with 4000 more glyphs took 19.9 ms. The bench compares a nearly empty terminal with a
   panel full of text.
3. Image state: `picture.wgsl` does `linear_to_srgb` (`pow`) per pixel on a non-sRGB target in its
   second pass, estimated 5–6 ms (not measured separately).
Smallest fix: choose the fragment entry point from `format.is_srgb()` in `Renderer::new`
(`spikes/s2-wgpu/src/gfx/render.rs:133`) so non-sRGB targets skip the `pow`; optionally a colour-only
pipeline for solid quads (upper bound measured: open 5.4 ms, closed 2.8 ms). **Open, needs the user:**
the change is in the shared `s2-wgpu` renderer (its own contract and offscreen tests for both surface
formats), and on a real GPU fragment cost of this size is normally invisible — the PC run of
`tooling/smoke/bench-run.sh` (or the sheet's typing-feel rows) decides whether it matters.
- Memory growth ≤ 80 MB with the largest image: **fail as measured**: +130 MB (245.1 vs 115.2)
  for a 64 MB RGBA texture; lavapipe keeps textures in process memory, so part or all of this is
  VRAM on a real GPU. Needs the PC run to judge. Finding S2.
- Back to baseline after close: **pass** for 4096² (117.2 vs 115.6 MB); a diagnostic 2048² run
  stayed at +32 MB after close (`/data/scratch/tmls-rs-v0/panel2/t7/diag-head-image-2048/`),
  consistent with glibc keeping freed blocks under its mmap threshold. Finding S3 (minor).
